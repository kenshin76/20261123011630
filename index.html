프로젝트 이해

핵심은 주문부터 정산·지급까지 근거를 연결하고, 담당자가 차이와 예외를 쉽게 확인할 수 있도록 만드는 것입니다. 주문상품별로 수집 → 공구(셀러·브랜드·조건) 연결 → 송장 → 취소·반품 반영 → 일 정산 → 지급 과정을 추적할 수 있는 통합 장부를 만들고, 원천 주문과 승인한 계산 예시로 정확성을 확인하겠습니다. 셀러와 브랜드가 포털에서 권한에 맞게 장부를 조회하고 정산서를 PDF·엑셀로 내려받을 수 있도록 해 반복적인 자료 요청도 줄이겠습니다.

아래 항목은 필요하실 때 눌러서 펼쳐 보실 수 있습니다.

2

핵심 수행 방안

펼쳐 보기접기
  1. 01

    합의한 정산 기준을 숫자로 검증한 뒤 전환

    현재 엑셀을 분석해 계산 예시가 포함된 정산 규칙 정의서를 G1에서 승인받고, 과거 1개월 재계산 대조(G3) → 오픈 후 8영업일 병행 대조를 시스템이 자동으로 수행합니다. 대조 과정에서 발견한 차이는 원인과 근거를 함께 설명하고, 엑셀 오류가 확인되면 수정한 기대값을 원천 주문·수식과 함께 제시해 승인받습니다. 설명되지 않는 차이 0원·미해결 중대 결함 0건을 확인한 뒤 엑셀 병행 운영을 마무리하며, 결함은 원인 설명에 그치지 않고 수정·재검증합니다.

  2. 02

    채널이 달라도 하나의 장부

    스마트스토어 주문은 커머스API를 통해 기본 10분 간격으로 자동 수집하고, 스룩페이 주문은 확인된 API 또는 담당자가 올린 엑셀을 통해 같은 장부에 반영합니다. 「채널 + 주문상품 행 식별자」로 중복을 막고, 수집에 실패하면 재시도 후 담당자에게 알립니다. 엑셀을 올리지 않은 일자·공구가 연결되지 않은 주문·매칭되지 않은 송장은 「확인 필요」 목록에서 안내해 담당자님이 해당 건을 우선 확인하실 수 있도록 합니다.

  3. 03

    정산 조건과 지급 결과를 끝까지 추적

    G1에서 정한 원천 주문 기준 시각에 유효한 수수료·공급가 조건을 보존해 지연 수집·재수집에도 유지합니다. 정산은 「작성 → 검토 → 확정 → 지급」 순서로 진행하며, 확정 후 변경은 다음 정산의 조정 항목으로 남기고 음수 금액은 지급하지 않고 이월합니다. 계좌가 변경되면 지급을 보류하고 재확인하며, 같은 정산의 중복 지급을 차단합니다. 은행 이체 결과가 확인되지 않은 건은 재지급을 보류하고, 실패가 확정된 건만 담당자 확인 후 재처리합니다. 파일 다운로드만으로 지급 완료 처리하지 않습니다.

원천징수 3.3% 계산은 개인 여부만으로 일괄 적용하지 않고, 귀사 세무 대리인이 확인한 대상·과세표준·세율·절사 기준·적용일을 반영합니다. 판매가·공급가·수수료의 부가세 포함 여부와 반올림 기준도 G1에서 계산 예시로 확정합니다.

수행 조건

펼쳐 보기접기
기술
운영자 웹과 포털은 React·TypeScript의 공통 코드를 활용해 개발 비용을 줄입니다. 정산 확정과 이력을 한 묶음으로 저장하는 서버에는 Java·Spring Boot를, DB에는 라이선스 비용 없는 관리형 MySQL을 사용합니다. 클라우드·도메인은 처음부터 귀사 명의로 구성하고 서버에 고정 IP를 적용합니다.
보안·개인정보
셀러·브랜드는 운영자 승인 후 이용하며, 서버에서 매 요청마다 접근 권한을 확인해 자기 데이터만 열람할 수 있도록 합니다. 셀러 화면의 구매자 정보는 가리고, 브랜드에는 배송에 필요한 기간에만 제공하며, 합의한 보관 기간 경과 후 자동 파기합니다. 계좌번호는 암호화 저장합니다.
인수 기준
승인한 기대값을 기준으로 설명되지 않는 정산 차이 0원·미해결 중대 결함 0건, 주문 누락·중복 0건, 이체 파일 은행 업로드·결과 반영, 타사 데이터 접근 차단, G1에서 합의한 처리 규모·성능 기준, 귀사 환경 재배포를 시험합니다.
결과물
전체 소스코드(귀사 소유 저장소)·DB 스키마, 요구사항 정의서·화면 설계서, 정산 규칙 정의서, 외부 연동 규격서, 대조 리포트·전환 확인서, 운영 매뉴얼·포털 안내.

담당자가 판매자센터 주문·상태 엑셀을 올리면 시스템이 검증·중복 차단·장부 반영·정산 대조를 처리합니다. 상품·가격·재고·송장은 확인된 일괄 업로드 양식의 엑셀을 생성해 담당자가 채널에 올립니다. 일괄 업로드가 없는 항목은 입력 자료 생성 + 담당자 화면 입력, 결과 파일이 없으면 상품번호·처리 결과를 직접 확인하는 절차를 G1에서 합의합니다. G1까지 규격·권한이 확인된 API와 엑셀 처리는 견적에 포함하며, 이후 새 API 전환은 장부·정산 구조를 재사용하되 별도 견적·일정을 승인받아 진행합니다.
사전 질문 Q2. 커머스API 연동 경험은?
스마트스토어 커머스API의 주문 수집·상품 등록 납품 실적은 없습니다. 관련 경험으로 7개 앱마켓 통합 빌링(2017년부터)과 복수 PG 결제·환불 연동(2024년부터)을 수행했습니다. 외부 API·중복 검증·상태 관리 경험을 적용하고, 착수 1주차에 귀사 명의 신청·애플리케이션 등록을 지원한 뒤 2주차에 주문 시험 조회·상품 시험 등록을 진행해 권한·호출 한도·제공 필드를 확인하겠습니다. 권한 확보가 지연되면 엑셀 방식으로 선행 개발하고, 연동 방식과 일정 영향을 G1에서 함께 확인하겠습니다.

착수 직후 신청을 지원하고, 늦어지는 항목은 엑셀·시험 환경으로 선행 개발합니다. G1 이후 새 API 전환은 별도 견적·일정을 먼저 안내합니다.
병행 운영 부담·설 연휴
시스템이 자동 대조하고 담당자님은 차이와 예외를 확인합니다. 연휴에도 API 수집·일자별 정산 초안은 유지하고, 엑셀 채널은 합의한 업로드 주기에 맞춰 반영하며 미제출 자료는 확인 목록으로 안내합니다. 검토·지급은 합의한 영업일에 진행하고, 인수 기준 미달 시 수정·재검증 후 검수합니다.
